## P1 — must fix before this round ships

### 1. EngineTask repair uses the wrong hash → RAM silently dies after the FIRST engine update
`StartupWindow.RepairStaleEngineTaskAsync` (StartupWindow.xaml.cs:260-266) stores the *extraction folder name* as `App.Settings.EngineTaskHash`:

```csharp
string bundleHash = Path.GetFileName(Path.GetDirectoryName(exePath)) ?? "";
```

but `EngineBundle` keys the folder by the **bundle's SHA-256**, while `DefaultExePath()` can legitimately return the `vendor\` fallback (no bundle extraction). In the fallback case the "hash" is `OpenRGB Windows 64-bit` — a constant — and the repair-once-per-bundle guard is meaningless (either always blocks after one declined prompt, or never distinguishes bundles).

Fix: use the bundle's real identity — `SDK.EngineBundle.CurrentHash()` (expose it if private), falling back to `"vendor"` only when `DefaultExePath()` returned the vendor path. Also guard `bundleHash == "vendor"` from ever being recorded.

### 2. Cancelling the UAC prompt crashes the app (unhandled OperationCanceledException)
Chain: user closes the splash (X / Alt+F4) or declines... actually even without declining — user clicks X while `EngineTask.Register`'s UAC prompt is up → `OnClosed` → `_cts.Cancel()` → the awaited `Task.Run(() => EngineTask.Register(...))` returns and execution continues to `await Task.Delay(1500, _cts.Token)` (StartupWindow.xaml.cs:290) → OCE propagates out of `RunAsync` → `Loaded += async (_,_) => { await RunAsync(); }` has no try/catch → on an `async void` lambda with **no** DispatcherUnhandledException handler anywhere in App.xaml.cs → process crash.

Even in the happy path the repair loop continues *after* close: `Manager!.Stop()` + `EngineTask.EndTaskInstance()` + `Manager!.RestartAsync(...)` run on a closed window.

Fix (two small pieces):
1. Wrap the `Loaded` handler body: `try { await RunAsync(); } catch (OperationCanceledException) { }` — plus a general `catch { }` for robustness.
2. First line of every repair/detect loop iteration: `if (!_cts.Token.IsCancellationRequested && IsVisible) ...` — or simpler: check `_cts.Token.ThrowIfCancellationRequested()` at the top of `RepairStaleEngineTaskAsync`, and bail out of the post-repair restart when cancelled instead of `try { } catch { }` swallowing it.

### 3. StartupWindow cleanup race: engine outlives the window
`Abort_Click` sets `_cts.Cancel()` and closes, but `RunAsync` may be mid-`RepairStaleEngineTaskAsync`, whose outer `catch { }` swallows the OCE and then still calls `Manager!.Stop()` + `EngineTask.EndTaskInstance()` + `Manager!.RestartAsync(60s)` on a closed window — the engine is restarted *after* the user asked to quit. Fix: re-throw OCE at the top of the outer catch (keep the general swallow) and skip the post-repair restart when `_cts.Token.IsCancellationRequested || !IsVisible`.

## P2 — should fix this round

### 4. `TaskStartError` is written but never read by anyone
`OpenRgbProcessManager.TaskStartError` (set at OpenRgbProcessManager.cs:175 & 212) has **zero consumers** outside its own file (verified: `grep TaskStartError src/ | grep -v OpenRgbProcessManager` → 0 hits). The new stale-task branch exists only to be *reported* — the plan was for the GUI to surface it or offer re-register.

Either: (a) after `StartAsync`, if `TaskStartError` is stale-task, have `MainWindow.ConnectAsync` show the Hardware-page state; or (b) delete the property. Dead code in a diagnostic property invites future misuse.

### 5. `EngineTaskHash` is written but nothing OFFERS re-register based on stale-ness at startup
The startup repair handles the flow, but the setting `EngineTaskHash`/`EngineTaskDeclined` pair is only ever read in StartupWindow. If the user declines at startup, the ONLY remaining path is Hardware → RGB RAM row (already correct, `adv.ram.stale` → Re-register button, Settings.cs:302-309). Good. But the declined state means **every launch until the next bundle change** runs the engine unelevated with no banner anywhere: RAM is silently missing. The Hardware page shows it only when visited. Suggestion: a tray balloon or status-bar hint once per declined launch ("RGB RAM needs re-registration — see Hardware"), driven by `TaskIsStale` result after StartAsync.

### 6. fxtest gate: verify.sh captured no output
`bash tools/verify.sh Debug` reported `no output captured: --fxtest --seconds=14` even though a manual run of the same exe with the same flags works fine (devices=4, errors=0). The script's PowerShell `Start-Process` capture lost output this session. Check verify.sh's fxtest leg for a redirect/encoding regression — a CI-style gate that reports "no output" is a false-negative gate.

**Suspect:** verify.sh runs fxtest while the live GUI (PID 17240, dist22) is holding the SDK port — StartAsync would attach to the live engine... it should still print. The capture failure is unexplained; re-run when the GUI is closed and confirm before trusting this gate.
